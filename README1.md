این یک تغییر مسیر بسیار هوشمندانه است. انتقال از اپلیکیشن دسکتاپ (Qt) به یک **اپلیکیشن تحت وب (Web App)** با استفاده از **جاوااسکریپت خالص** و **Material Design** ، مشکل نصب و سازگاری با سیستمعامل‌های مختلف را یک‌بار برای همیشه حل می‌کند. در این معماری جدید، مرورگر کاربر (حتی روی گوشی) به عنوان رابط کاربری (GUI) عمل می‌کند و ESP32 تنها نقش یک **سرور وب** و **پل ارتباطی با سخت‌افزار** را ایفا خواهد کرد.

### 🧩 کتابخانه‌های کلیدی برای پیاده‌سازی

خبر خوب این است که برای هر بخش از این اپلیکیشن وب، کتابخانه‌های آماده و کاملاً رایگانی وجود دارد:

#### ۱. هگز ادیتور (Hex Editor)

*   **گزینه اول (پیشنهادی):** [`vuehex`](https://www.npmjs.com/package/vuehex) - یک کامپوننت هگز ادیتور بسیار سریع و حرفه‌ای برای **Vue 3** است.
    *   **مزایا:** بسیار سبک (حدود 72KB)، بدون وابستگی، از داده‌های حجیم پشتیبانی می‌کند، قابلیت ویرایش، کپی/پیست و هایلایت‌کردن دلخواه را دارد.
*   **گزینه دوم:** [`hexedit-js`](https://github.com/dnlmlr/hexedit-js) - یک کتابخانه بسیار ساده و سبک با **جاوااسکریپت خالص (Vanilla JS)** که به راحتی در هر پروژه‌ای قابل استفاده است.
*   **گزینه سوم:** [`hex-works`](https://github.com/reproteq/hex-works) - یک نمونه کامل از یک هگز ادیتور تحت وب که با **AngularJS** و **Material Design** ساخته شده است و می‌توانید از کدهای آن ایده بگیرید.

#### ۲. ترمینال سریال (Serial Terminal)

برای نمایش خروجی‌های دیباگ و ارتباط با UART هدف، به یک ترمینال در مرورگر نیاز دارید.

*   **پیشنهاد:** [`xterm.js`](https://xtermjs.org/) - محبوب‌ترین کتابخانه برای شبیه‌سازی ترمینال در مرورگر است که در پروژه‌های بزرگی مانند VS Code نیز استفاده می‌شود. یک نمونه پروژه به نام [`Termino.js`](https://github.com/MarketingPipeline/Termino.js) نیز وجود دارد که کار را ساده‌تر می‌کند.

#### ۳. ارتباط با ESP32 (HTTP و WebSocket)

برای ارسال و دریافت داده و دستورات بین مرورگر و ESP32 از دو روش استفاده می‌شود:

*   **HTTP (REST API):** برای عملیات‌های سنگین مثل آپلود فایل و دریافت اطلاعات وضعیت.
*   **WebSocket:** برای ارتباط دوطرفه و لحظه‌ای، مخصوصاً برای دیباگ و ترمینال که نیاز به سرعت بالایی دارند.

#### ۴. مدیریت فیوزبیت‌ها (Fuse Bits)

برای این بخش، یک رابط کاربری گرافیکی (GUI) سفارشی با استفاده از **Material Design** طراحی می‌شود. می‌توانید از ایده‌های موجود در پروژه‌هایی مثل **AVR8 Burn-O-Mat** (که یک GUI جاوا برای `avrdude` است) استفاده کنید و آن را به صورت یک صفحه وب با چک‌باکس‌ها و توضیحات هر فیوز پیاده‌سازی کنید. همچنین پروژه `ISPHIDIUS WebHID App` یک نمونه عالی از یک رابط کاربری تحت وب برای تنظیم فیوزبیت‌های AVR است.

#### ۵. دیباگ JTAG/SWD

برای پیاده‌سازی دیباگ از طریق وب، می‌توانید از یک پروژه منبع‌باز فوق‌العاده به نام **ESP32JTAG** الهام بگیرید.

*   **ESP32JTAG** یک ابزار حرفه‌ای است که روی **ESP32 ** اجرا می‌شود و قابلیت‌های زیر را از طریق یک **رابط کاربری تحت وب** ارائه می‌دهد:
    *   دیباگ JTAG/SWD (سازگار با OpenOCD)
    *   برنامه‌ریزی FPGA
    *   ترمینال UART
    *   آنالایزر منطقی ۱۶ کاناله با فرکانس ۲۵۰ مگاهرتز

این پروژه نشان می‌دهد که **ایده شما نه تنها شدنی است، بلکه دقیقاً مسیری است که ابزارهای حرفه‌ای بازار نیز در حال حرکت به سمت آن هستند**.

### 🚀 گام‌های عملی برای شروع

1.  **طراحی سخت‌افزار:** مشابه نقشه قبلی، اما با این تفاوت که ESP32 باید حافظه فلش کافی (حداقل ۴ مگابایت) برای میزبانی فایل‌های رابط کاربری داشته باشد.
2.  **پیاده‌سازی وب‌سرور روی ESP32:** از کتابخانه‌های استاندارد ESP-IDF یا Arduino برای راه‌اندازی یک وب‌سرور ساده استفاده کنید که فایل‌های استاتیک (HTML, CSS, JS) را سرو کند و یک سری **API Endpoint** برای دریافت دستورات داشته باشد.
3.  **توسعه رابط کاربری (Frontend):**
    *   از یک فریم‌ورک مدرن مانند **Vue 3** (به همراه `vuehex`) یا حتی **Vanilla JS** استفاده کنید.
    *   برای ظاهر، از **Material Design** و کتابخانه‌هایی مانند **Materialize** یا **Vuetify** (اگر Vue انتخاب کنید) بهره ببرید.
    *   صفحه‌های مختلف را طراحی کنید: صفحه اصلی (انتخاب میکروکنترلر)، صفحه هگز ادیتور، صفحه تنظیمات فیوزبیت، و صفحه ترمینال/دیباگ.
4.  **اتصال به سخت‌افزار:** در سمت سرور (ESP32)، دستورات دریافتی از API را به سیگنال‌های مناسب روی پین‌ها (SPI، I2C، JTAG و غیره) تبدیل کنید.

### 💎 جمع‌بندی
ایده‌ی "ال‌پروگرمر" دقیقاً همان چیزی است که اکوسیستم متن‌باز به آن نیاز دارد. با توجه به تجربه‌ی شما و وجود پروژه‌های پایه‌ی عالی، این هدف نه تنها شدنی، بلکه یک گام منطقی و تحول‌آفرین است. در زیر، یک **پروپوزال کامل** برای این پروژه تدوین شده است.

## پروپوزال پروژه: ال‌پروگرمر (L-Programmer)
### یک پروگرمر و دیباگر جهانی، بی‌سیم و تحت وب

---

### ۱. چشم‌انداز (Vision)

ایجاد یک **پروگرمر و دیباگر جهانی، بی‌سیم و مبتنی‌بروب** که بتواند هر نوع میکروکنترلر، حافظه و FPGA را برنامه‌ریزی و دیباگ کند. این ابزار، جایگزین طیف وسیعی از ابزارهای تخصصی (مانند ST-Link، J-Link، USBasp، CH341A و هولتک و میکرو چیپ ...) خواهد شد و با ارائه‌ی یک رابط کاربری وب‌محور یکپارچه، فرآیند توسعه را برای مهندسان، هکرهای سخت‌افزاری و علاقه‌مندان به الکترونیک، ساده‌تر، سریع‌تر و قابل‌دسترس‌تر می‌کند.

### ۲. مأموریت (Mission)

توسعه و ارائه‌ی یک راه‌حل سخت‌افزاری و نرم‌افزاری متن‌باز که با استفاده از یک تراشه‌ی ESP32 ، امکان برنامه‌ریزی و دیباگ بی‌سیم را برای طیف گسترده‌ای از اهداف (Targets) فراهم کند. این پروژه بر **سادگی استفاده، قدرت عملکرد و قابلیت گسترش** تأکید دارد.

### ۳. معماری سیستم (System Architecture)

معماری ال‌پروگرمر بر پایه‌ی یک برد سخت‌افزاری قدرتمند و یک پلتفرم نرم‌افزاری وب‌محور طراحی شده است.

#### ۳.۱. سخت‌افزار (Hardware)

*   **پردازنده مرکزی:** ESP32  با حافظه‌ی PSRAM حداقل ۸ مگابایت برای اجرای همزمان وب‌سرور و پردازش‌های سنگین.
*   **منبع تغذیه:**
    *   ورودی USB-C (۵ ولت).
    *   تنظیم‌کننده‌های ولتاژ برای تولید ۳.۳ ولت و ۵ ولت.
    *   **مبدل افزاینده (Boost Converter) قابل کنترل:** برای تولید ولتاژهای بالاتر مانند ۱۲ ولت یا ۱۳ ولت (مورد نیاز برای برنامه‌ریزی High-Voltage برخی میکروکنترلرها مانند PIC و AVR).
*   **مبدل‌های سطح منطقی (Level Shifters):**
    *   برای تطبیق ولتاژ ۳.۳ ولت ESP32 با اهداف ۱.۸، ۳.۳ و ۵ ولت.
    *   **چالش کلیدی:** برای پروتکل‌های دوطرفه مانند SWD، نیاز به استفاده از تراشه‌های Level Shifter با قابلیت کنترل جهت‌دهی (مانند SN74LVC1T45) است تا از مشکلات رایج در پروژه‌های مشابه جلوگیری شود.
*   **حافظه:** فلش حداقل ۱۶ مگابایت برای ذخیره‌سازی firmware و فایل‌های رابط کاربری وب.
*   **کانکتورها:** یک کانکتور ۱۰ پین یا ۲۰ پین استاندارد برای اتصال به اهداف مختلف که تمامی سیگنال‌های مورد نیاز (SWD، JTAG، SPI، I2C، UART، VCC، GND و VPP) را در خود جای دهد.

#### ۳.۲. نرم‌افزار (Software)

معماری نرم‌افزار به دو بخش اصلی **Firmware (ESP32)** و **Frontend (وب)** تقسیم می‌شود.

##### **Firmware (ESP32)**

1.  **لایه ارتباطی:** یک وب‌سرور تعبیه‌شده برای میزبانی فایل‌های Frontend و ارائه‌ی APIهای RESTful و WebSocket برای ارتباط دوطرفه با مرورگر.
2.  **لایه پروتکل:** پیاده‌سازی یا یکپارچه‌سازی پروتکل‌های زیر:
    *   **CMSIS-DAP از طریق TCP/IP:** برای دیباگ و برنامه‌ریزی ARMهای Cortex-M با استفاده از OpenOCD. پروژه‌هایی مانند `cmsis_dap_tcp_esp32` و `wireless_dap` پایه‌های محکمی برای این بخش هستند.
    *   **پروتکل‌های عمومی (Bus Pirate Mode):** برای ارتباط با انواع سنسورها و حافظه‌ها از طریق پروتکل‌های I2C، SPI، UART، 1-Wire و .... پروژه‌ی `ESP32 Bit Pirate` یک پیاده‌سازی کامل و ماژولار از این قابلیت‌ها ارائه می‌دهد.
    *   **پروتکل‌های تخصصی:** AVR ISP (مشابه USBasp)، PIC Programming و SPI Flash Programming (مشابه CH341A).
3.  **لایه سخت‌افزاری:** درایورهایی برای کنترل مستقیم GPIOها با سرعت بالا و پشتیبانی از ویژگی‌هایی مانند **SPI Acceleration** برای افزایش سرعت برنامه‌ریزی (تا ۴۰ مگاهرتز).

##### **Frontend (وب‌اپلیکیشن)**

یک **Single-Page Application (SPA)** مدرن و واکنش‌گرا (Responsive) که با استفاده از HTML، CSS (با چارچوب Material Design) و JavaScript نوشته می‌شود.

*   **مدیریت حالت (State Management):** برای مدیریت وضعیت اتصال، تنظیمات و داده‌ها.
*   **هگز ادیتور:** یک کامپوننت قدرتمند برای مشاهده و ویرایش داده‌های باینری (فایل‌های HEX، BIN).
*   **مدیریت فیوزبیت‌ها:** یک رابط کاربری گرافیکی و هوشمند که بر اساس نوع میکروکنترلر انتخاب‌شده، فیوزبیت‌های مربوطه را با توضیحات کامل نمایش می‌دهد.
*   **ترمینال سریال:** یک ترمینال تعبیه‌شده (مانند xterm.js) برای ارتباط سریال با هدف از طریق UART-to-TCP Bridge.
*   **کنسول دیباگ:** برای نمایش خروجی‌های دیباگ و ارتباط با GDB Server.

### ۴. برنامه‌ی توسعه (فازبندی)

پروژه در **۴ فاز اصلی** برنامه‌ریزی شده است تا به صورت کنترل‌شده و با کمترین ریسک پیش رود.

#### **فاز ۱: پایه‌سازی و تست Frontend (هفته ۱-۲)**

*   **هدف:** ایجاد یک نمونه‌ی اولیه (Prototype) از رابط کاربری وب و اطمینان از عملکرد صحیح هگز ادیتور.
*   **فعالیت‌ها:**
    *   راه‌اندازی یک پروژه‌ی وب ساده (با استفاده از Vue.js یا React).
    *   پیاده‌سازی یا یکپارچه‌سازی کامپوننت هگز ادیتور.
    *   پیاده‌سازی قابلیت‌های بارگذاری، ذخیره و ویرایش فایل‌های HEX و BIN.
    *   طراحی اولیه‌ی صفحات با چارچوب Material Design.
*   **خروجی:** یک اپلیکیشن وب کاملاً آفلاین که قابلیت ویرایش فایل‌های هگز را دارد و می‌تواند به عنوان یک ابزار مستقل نیز مورد استفاده قرار گیرد.

#### **فاز ۲: توسعه‌ی Firmware پایه (هفته ۳-۴)**

*   **هدف:** راه‌اندازی وب‌سرور روی ESP32 و برقراری ارتباط اولیه با مرورگر.
*   **فعالیت‌ها:**
    *   پیاده‌سازی وب‌سرور روی ESP32  برای سرو کردن فایل‌های استاتیک.
    *   پیاده‌سازی یک API ساده (مانند دریافت اطلاعات دستگاه، وضعیت پین‌ها).
    *   تست ارتباط WiFi و اتصال مرورگر به آدرس IP دستگاه.
*   **خروجی:** یک ESP32 که یک صفحه‌ی وب ساده را میزبانی می‌کند و می‌تواند به درخواست‌های اولیه پاسخ دهد.

#### **فاز ۳: پیاده‌سازی پروتکل‌های اصلی (هفته ۵-۸)**

*   **هدف:** اضافه کردن قابلیت‌های برنامه‌ریزی و دیباگ.
*   **فعالیت‌ها:**
    *   **مرحله ۱:** یکپارچه‌سازی کد پروژه‌ی `cmsis_dap_tcp_esp32` برای پشتیبانی از **JTAG/SWD** و اتصال به OpenOCD.
    *   **مرحله ۲:** اضافه کردن پشتیبانی از **EEPROM/Flash** از طریق پروتکل‌های I2C و SPI با الهام از `ESP32 Bit Pirate`.
    *   **مرحله ۳:** پیاده‌سازی **AVR ISP** برای برنامه‌ریزی میکروکنترلرهای AVR (مانند ATmega328).
    *   **مرحله ۴:** تست کامل هر پروتکل با اهداف واقعی و رفع اشکالات.
*   **خروجی:** یک دستگاه که می‌تواند حداقل سه خانواده‌ی اصلی (ARM, AVR, EEPROM/Flash) را برنامه‌ریزی کند.

#### **فاز ۴: تکمیل، بهینه‌سازی و انتشار (هفته ۹-۱۲)**

*   **هدف:** کامل کردن قابلیت‌ها، بهبود رابط کاربری و آماده‌سازی برای انتشار.
*   **فعالیت‌ها:**
    *   اضافه کردن پشتیبانی از پروتکل‌های بیشتر (PIC، FPGA و ...).
    *   پیاده‌سازی قابلیت **دیباگ (Debugging)** از طریق وب (ارتباط با GDB Server).
    *   بهینه‌سازی سرعت و مصرف حافظه.
    *   طراحی نهایی PCB و ساخت نمونه‌های اولیه.
    *   نوشتن مستندات کامل (راهنمای ساخت، راهنمای کاربر، API Reference).
    *   انتشار پروژه به صورت متن‌باز روی GitHub.
*   **خروجی:** نسخه‌ی نهایی و پایدار پروژه به همراه تمام مستندات و فایل‌های ساخت.

### ۷. جمع‌بندی

پروژه‌ی "پروگرمر همه کاره" با تکیه بر تجربیات ارزشمند شما و استفاده از پروژه‌های متن‌باز موفق، پتانسیل تبدیل شدن به یک ابزار **انقلابی** در اکوسیستم توسعه‌ی سخت‌افزار را دارد. با یک برنامه‌ریزی دقیق و اجرای مرحله‌به‌مرحله، می‌توان به ابزاری دست یافت که **هزینه‌ها را کاهش، سرعت توسعه را افزایش و پیچیدگی‌های کار با ابزارهای متعدد را برای همیشه برطرف می‌کند.**

گام بعدی، شروع **فاز ۱** یعنی طراحی اولیه‌ی رابط کاربری وب و تست هگز ادیتور است.چه ایده‌ی جذابی! ترکیب «همه‌کاره بودن»، «فعال‌سازی مثل وین‌رار» و «رابط کاربری تحت وب با جاوااسکریپت خالص» واقعاً می‌تونه یه ابزار انقلابی باشه. بیایین مرحله به مرحله پیش بریم.

### 🧱 ۱. سخت‌افزار: از کجا شروع کنیم؟

*   **ولتاژ ۵ ولت و ESP32**: اولین نکته‌ی مهم اینه که **پین‌های ESP32 به طور رسمی ۵ ولت نیستند** و دادن ولتاژ ۵ ولت مستقیم به اونها می‌تونه به چیپ آسیب بزنه. برای کار با اهداف ۵ ولتی، حتماً به یک **مبدل سطح ولتاژ (Level Shifter)** نیاز دارید. این کار باعث میشه که پروژه حرفه‌ای‌تر و ایمن‌تر بشه.
*   **پایه و اساس**: برای شروع، می‌تونید از یک برد آماده مثل **ESP32-DevKit** یا **XIAO ESP32C6** استفاده کنید. این کار شما رو از پیچیدگی‌های اولیه‌ی ساخت برد نجات میده و اجازه میده سریعتر روی نرم‌افزار تمرکز کنید.
*   **منابع الهام**: پروژه‌هایی مثل [`cmsis_dap_tcp_esp32`](https://github.com/bkuschak/cmsis_dap_tcp_esp32) و [`espprog`](https://github.com/jnicolson/espprog) می‌تونن راهنمای خوبی برای نحوه‌ی اتصال پین‌ها و طراحی سخت‌افزار باشند.

### 💻 ۲. نرم‌افزار: هسته‌ی اصلی پروژه

طبق درخواست خودتون، از **جاوااسکریپت خالص (Vanilla JS)** در فرانت‌اند و **ESP-IDF** در بک‌اند استفاده می‌کنیم.

*   **معماری کلی**: ESP32 یه **وب‌سرور** راه‌اندازی می‌کنه که صفحه‌ی وب (شامل Hex Editor، تنظیمات فیوزبیت و ...) رو به مرورگر کاربر میده. ارتباط بین مرورگر و ESP32 از طریق **WebSocket** یا **HTTP API** انجام میشه.
*   **ارتباط با هدف**: برای برنامه‌ریزی و دیباگ، از پروتکل‌های استاندارد استفاده می‌کنیم:
    *   **STM32 و ARM**: از پروژه‌ی [`cmsis_dap_tcp_esp32`](https://github.com/bkuschak/cmsis_dap_tcp_esp32) استفاده کنید که به ESP32 اجازه میده از طریق **JTAG** یا **SWD** با اهداف ARM ارتباط برقرار کنه. این پروژه با **OpenOCD** روی کامپیوتر شما کار می‌کنه.
    *   **AVR (مثل ATmega)**: می‌تونید از پروتکل **ISP** با الهام از ابزارهایی مثل `avrdude` استفاده کنید.
    *   **Holtek**: این شرکت برای برنامه‌ریزی سریال (ISP) از پروتکل‌های **USART** یا **USB** استفاده می‌کنه. با مطالعه‌ی دیتاشیت‌ها، می‌تونید این پروتکل رو روی ESP32 پیاده‌سازی کنید.
*   **ابزارهای آماده در مرورگر**: برای فلش کردن خود ESP32 از طریق مرورگر، کتابخانه‌های آماده‌ای مثل [`esptool-js`](https://github.com/espressif/esptool-js) وجود دارن که از **Web Serial API** استفاده می‌کنن. این نشون میده که چنین قابلیتی کاملاً شدنیه.

### 🧩 ۳. ماژولار کردن کد (قابلیت آپدیت)

برای اینکه بتونید به راحتی میکروکنترلرهای جدید اضافه کنید، کد رو به صورت ماژولار طراحی کنید:

1.  **لایه‌ی پروتکل (Protocol Layer)**: برای هر خانواده (مثل `avr_isp.c`, `stm32_swd.c`, `holtek_isp.c`) یه فایل مجزا در نظر بگیرید که تابع‌های استانداردی مثل `init()`, `read()`, `write()`, `erase()` رو داشته باشه.
2.  **لایه‌ی سخت‌افزار (Hardware Abstraction Layer - HAL)**: توابعی بنویسید که مستقیماً با پین‌های ESP32 کار کنن. به این ترتیب، لایه‌ی پروتکل می‌تونه بدون تغییر، از هر پین‌بندی استفاده کنه.
3.  **سیستم پلاگین (Plugin System)**: برای اضافه کردن پشتیبانی از یک میکرو جدید، کافیه یه فایل جدید به پوشه‌ی `protocols` اضافه کنید و نامش رو در تنظیمات وب‌سرور ثبت کنید. بقیه‌ی کارها به صورت خودکار انجام میشه.

با این طراحی، توسعه‌ی پروژه به مراتب ساده‌تر و سریع‌تر خواهد شد.

### 💰 ۴. مدل کسب‌وکار: مثل وین‌رار

ایده‌ی شما برای مدل درآمدی جذابه. می‌تونید اینطور پیاده‌اش کنید:

*   **نسخه‌ی رایگان (Free Tier)**: شامل قابلیت‌های پایه مثل Hex Editor، فلش کردن فایل‌های `.hex` و `.bin` برای تعداد محدودی از میکروها (مثلاً AVR و Arduino) باشه.
*   **نسخه‌ی حرفه‌ای (Pro Tier)**: با فعال‌سازی (مثلاً با وارد کردن یه کلید)، قابلیت‌های پیشرفته‌تری مثل دیباگ (JTAG/SWD)، پشتیبانی از میکروهای تخصصی‌تر (STM32، Holtek، PIC) و تنظیمات پیشرفته‌ی فیوزبیت فعال بشه.
*   **روش فعال‌سازی**: فعال‌سازی می‌تونه از طریق یه درخواست آنلاین به سرور شما (برای بررسی کلید) یا با استفاده از یه الگوریتم آفلاین (مثل فعال‌سازی ویندوز) انجام بشه.

### 🗺️ ۵. نقشه‌ی راه (Roadmap) پیشنهادی

برای اینکه پروژه رو یک‌بار برای همیشه درست پیش ببرید، این مسیر رو پیشنهاد می‌کنم:

1.  **فاز صفر (آماده‌سازی)**: مطالعه‌ی دقیق پروژه‌های مشابه مثل `cmsis_dap_tcp_esp32` و `esptool-js` برای درک عمیق‌تر.
2.  **فاز اول (هسته)**: راه‌اندازی وب‌سرور روی ESP32 و طراحی صفحه‌ی اولیه با Hex Editor (با جاوااسکریپت خالص).
3.  **فاز دوم (AVR)**: پیاده‌سازی پروتکل ISP برای AVR و تست با یه برد ساده مثل Arduino Uno.
4.  **فاز سوم (STM32)**: یکپارچه‌سازی کد `cmsis_dap_tcp_esp32` برای پشتیبانی از SWD/JTAG.
5.  **فاز چهارم (سایر)**: اضافه کردن پشتیبانی از Holtek، PIC و دیگر میکروها با استفاده از معماری ماژولار.
6.  **فاز پنجم (تکمیل)**: طراحی PCB نهایی، اضافه کردن مدار Level Shifter، پیاده‌سازی سیستم فعال‌سازی و انتشار پروژه.

### 🗺️ نقشه‌ی راه (اولویت‌های آینده)

#### فاز ۱: تکمیل داده‌ها و رفع باگ‌های فرانت‌اند (هفته‌ی اول)

- [ ] **اجرای اسکریپت تبدیل XML برای PIC** و تولید فایل `pic-fuses.js` کامل.
- [ ] **تکمیل داده‌های Holtek** با مراجعه به دیتاشیت‌ها (در صورت دسترسی).
- [ ] **رفع مشکل ذخیره‌سازی HEX برای PIC** با استفاده از نقشه‌ی حافظه و اندازه‌های واقعی.
- [ ] **بهبود نمایش فیوزبیت PIC** با اضافه کردن چک‌باکس‌های قابل ویرایش (در صورت نیاز).
- [ ] **تست هگز ادیتور با فایل‌های بزرگ** و بهینه‌سازی عملکرد صفحه‌بندی.

#### فاز ۲: پیاده‌سازی Firmware ESP32 (هفته‌ی دوم تا چهارم)

- [ ] **راه‌اندازی وب‌سرور روی ESP32** با استفاده از `mongoose` یا `esp_http_server`.
- [ ] **پیاده‌سازی APIهای اصلی**:
  - `GET /api/devices` – لیست دستگاه‌ها (از رجیستری JS به ESP32 منتقل شود یا در ESP32 کد شود).
  - `POST /api/connect` – اتصال به دستگاه هدف (تنظیم ولتاژ و سیگنال‌ها).
  - `POST /api/flash` – دریافت داده‌های HEX و اجرای الگوریتم برنامه‌ریزی (ISP/SWD).
  - `POST /api/read` – خواندن حافظه (Flash/EEPROM/Config) و بازگرداندن داده.
- [ ] **پیاده‌سازی پروتکل‌های سطح پایین**:
  - **ISP** برای AVR (با زمان‌بندی دقیق).
  - **ICSP** برای PIC (با پشتیبانی از ۱۰/۱۲/۱۶/۱۸F).
  - **SWD** برای ARM (با استفاده از کتابخانه‌های موجود مانند `CMSIS‑DAP`).
- [ ] **مدیریت ولتاژ VPP** (۱۲ ولت) با استفاده از مبدل Boost و کنترل نرم‌افزاری.

#### فاز ۳: اتصال فرانت‌اند به ESP32 واقعی (هفته‌ی پنجم)

- [ ] **جایگزینی APIهای شبیه‌سازی** با درخواست‌های واقعی به ESP32.
- [ ] **پیاده‌سازی WebSocket** برای ارتباط لحظه‌ای (ترمینال، دیباگ).
- [ ] **تست یکپارچگی** با اتصال به چند دستگاه واقعی (مثلاً ATmega328P و PIC18F4550).

- [ ] **افزودن پشتیبانی از خانواده‌های جدید** (STM32، ESP32، AVR XMEGA).

## 🛠️ مدار کمکی (VPP Boost)

یک مبدل بوست ۵→۱۲V (مثل MT3608) روی برد طراحی کنید.  
GPIO16 (VPP_EN) به پایهٔ Enable مبدل وصل شود.  
وقتی پروتکل PIC انتخاب می‌شود، GPIO16 را HIGH کنید تا ۱۲V روی پایهٔ ۱۰ کانکتور بیاید.  
هنگام اتصال PIC، کافیست پایهٔ MCLR تراشه را به این پین ۱۰ متصل کنید.

function getBaseAddress(family, section) {
  // اول از رجیستری خانواده بگیر
  const familyObj = registry.families.find(f => f.name === family);
  if (familyObj && familyObj.getBaseAddress) {
    return familyObj.getBaseAddress(section);
  }
  
  // اگر خانواده getBaseAddress نداشت، از memoryMap استفاده کن
  if (familyObj && familyObj.memoryMap && familyObj.memoryMap[section]) {
    return familyObj.memoryMap[section].start || 0x000000;
  }
  
  // fallback
  const fallbackMap = {
    'AVR':    { flash: 0x000000, eeprom: 0x810000, config: 0x820000, id: 0x910000 },
    'PIC':    { flash: 0x000000, eeprom: 0xF00000, config: 0x2007,   id: 0x2000 },
    'STM32':  { flash: 0x08000000, config: 0x1FFFF800, id: 0x1FFFF7E8 },
    'STM8':   { flash: 0x008000, eeprom: 0x004000, config: 0x004800, id: 0x004800 },
    'Holtek': { flash: 0x000000, eeprom: 0x00E000, config: 0x004000, id: 0x004010 },
    'ESP32':  { flash: esp32CustomAddr },
    'Serial': { flash: 0x000000 },
    'nRF24':  { flash: 0x00000000, config: 0x10001000, id: 0x10000000 },
    'CC25xx': { flash: 0x000000 },
  };
  
  const map = fallbackMap[family] || fallbackMap['AVR'];
  return map[section] || 0x000000;
}
```

function detectWordSize(family, deviceName) {
  const familyObj = registry.families.find(f => f.name === family);
  
  // اگر خانواده getWordSize داره، ازش استفاده کن
  if (familyObj && familyObj.getWordSize) {
    return familyObj.getWordSize(deviceName);
  }
  
  // از memoryMap بخون
  if (familyObj && familyObj.memoryMap) {
    // برای بخش flash
    if (familyObj.memoryMap.flash) {
      return familyObj.memoryMap.flash.wordSize || 8;
    }
  }
  
  // fallback
  if (family === 'PIC') return 14;
  if (family === 'STM32' || family === 'nRF24' || family === 'CC25xx') return 32;
  if (family === 'STM8') return 8;
  return 8;
}

async function doRead(section) {
  if (!currentDeviceName) {
    setStatus('⚠️ لطفاً ابتدا یک دستگاه انتخاب کنید.', true);
    return;
  }
  
  // گرفتن اطلاعات از خانواده
  const familyObj = registry.families.find(f => f.name === currentFamily);
  const memInfo = familyObj?.memoryMap?.[section] || {};
  const blockSize = memInfo.blockSize || 256;
  const totalSize = Math.min(memInfo.size || 2048, 2048); // Max 2KB for preview
  
  const baseAddr = getBaseAddress(currentFamily, section);
  
  setStatus(`📖 در حال خواندن ${section} (${blockSize} بایت در هر بلوک)...`);
  
  // اگر blockSize کمتر از totalSize باشه، باید چندبار بخونیم
  let allBytes = new Uint8Array(0);
  
  for (let offset = 0; offset < totalSize; offset += blockSize) {
    const size = Math.min(blockSize, totalSize - offset);
    const addr = baseAddr + offset;
    
    try {
      const readRes = await apiPost('/api/read', { address: addr, size: size });
      if (!readRes.success) break;
      
      const chunk = hexToBytes(readRes.data || '');
      const temp = new Uint8Array(allBytes.length + chunk.length);
      temp.set(allBytes);
      temp.set(chunk, allBytes.length);
      allBytes = temp;
      
      setStatus(`📖 خواندن ${section}... ${Math.min(offset + size, totalSize)}/${totalSize}`);
    } catch (err) {
      setStatus(`❌ خطا: ${err.message}`, true);
      break;
    }
  }
  
  if (!currentData) {
    currentData = { flash: new Uint8Array(0), eeprom: new Uint8Array(0), config: new Uint8Array(0), id: new Uint8Array(0) };
  }
  currentData[section] = allBytes;
  updateTabSizes();
  switchTab(section);
  setStatus(`✅ ${section} خوانده شد (${allBytes.length} بایت)`);
}

text

Device → Host (Header = 1):
┌─────────────────────────────────────────────────────────────┐
│  Header=1  │  D7  │  D6  │ ... │  D0  │  Parity  │  ACK  │
│  ────┐     │      │      │     │      │          │       │
│      │     │      │      │     │      │          │       │
│      └─────┘      └──────┘     └──────┘          └───────┘
│   LOW=1/3  │  LOW=2/3 │     │  LOW=2/3  │  LOW=2/3 │      │
│   HIGH=2/3 │  HIGH=1/3│     │  HIGH=1/3 │  HIGH=1/3│      │
└─────────────────────────────────────────────────────────────┘

نکات کلیدی:

    Header=1: LOW کوتاه (1/3) + HIGH بلند (2/3)

    Data bits:

        Bit 1: LOW کوتاه (1/3) + HIGH بلند (2/3)

        Bit 0: LOW بلند (2/3) + HIGH کوتاه (1/3)

    هر بیت با Falling Edge شروع می‌شود


اگر قصد داری این پروژه را کامل پیاده‌سازی کنی (در حد یک **ST-Link برای STM8**)، مرحله بعدی بررسی **مجموعه کامل دستورات SWIM** است؛ یعنی ساختار دقیق فریم‌های `ROTF`، `WOTF`، `SRST`، نحوه آدرس‌دهی حافظه‌های Flash/RAM/EEPROM، ترتیب بیت‌ها، و رفتار دستگاه در پاسخ به هر فرمان. این بخش از پروتکل مشخص می‌کند هر فرمان دقیقاً چه بایت‌هایی را روی خط SWIM ارسال و دریافت می‌کند.
من هم اگر هدف **سرعت، حجم کم و کار روی ESP32** باشد، با این تصمیم موافقم. لازم نیست مثل STLINK پروژه را به چند فایل تقسیم کنیم. یک فایل `protocol_swim.c` کاملاً مناسب است.

فقط پیشنهاد می‌کنم همان یک فایل را لایه‌بندی کنیم؛ یعنی ترتیب توابع منطقی باشد، نه اینکه از هم جدا شوند.

Command Frame (Host → Device)
text

[Header: 1 bit = 0] [b0] [b1] [b2] [Parity] [ACK]
     6 bits total

    5 بیت از Host ارسال می‌شود: Header(0) + b0 + b1 + b2 + Parity

    1 بیت از Device برمی‌گردد: ACK

Data Frame (Host → Device)
text

[Header: 1 bit = 0] [D7] [D6] [D5] [D4] [D3] [D2] [D1] [D0] [Parity] [ACK]
     11 bits total

    10 بیت از Host ارسال می‌شود: Header(0) + 8 Data + Parity

    1 بیت از Device برمی‌گردد: ACK

Data Frame (Device → Host)
text

[Header: 1 bit = 1] [D7] [D6] [D5] [D4] [D3] [D2] [D1] [D0] [Parity] [ACK]
     11 bits total

    10 بیت از Device ارسال می‌شود: Header(1) + 8 Data + Parity

    1 بیت از Host برمی‌گردد: ACK

## 📚 **آموزش کامل پروتکل SWIM و پیاده‌سازی برنامه‌نویسی STM8**

---

## 🎯 **مقدمه**
پروتکل **SWIM** (Single Wire Interface Module) یک پروتکل ارتباطی تک‌سیم است که برای برنامه‌ریزی و دیباگ میکروکنترلرهای **STM8** استفاده می‌شود. در این آموزش، گام‌به‌گام با این پروتکل آشنا می‌شوید.

---

## 🔌 **۱. اتصال سخت‌افزاری**
اتصال بسیار ساده است، فقط به **۳ سیم** نیاز دارید:

| پایه ESP32 | پایه STM8 | توضیح |
|-----------|----------|--------|
| GPIO18 (SWIM) | SWIM (PD1) | داده (Open-Drain با Pull-up ۱kΩ) |
| GPIO5 (NRST) | NRST | ریست سخت‌افزاری |
| GND | GND | زمین مشترک |

⚠️ **نکته:** یک مقاومت **۱kΩ** بین SWIM و VDD (۳.۳V) قرار دهید.

---

## ⚡ **۲. توالی فعال‌سازی (Entry Sequence)**
برای شروع ارتباط، میزبان باید یک توالی مشخص را روی پایه SWIM ارسال کند:

```
1. LOW به مدت 16 میکروثانیه
2. ۴ پالس 500µs (LOW/HIGH)
3. ۴ پالس 250µs (LOW/HIGH)
4. رها کردن باس (HIGH)
```

### **کد Entry:**
```c
GPIO.out_w1tc = SWIM_BIT;        // LOW
esp_rom_delay_us(16);

for (int i = 0; i < 4; i++) {
    GPIO.enable_w1tc = SWIM_BIT; // HIGH
    esp_rom_delay_us(500);
    GPIO.out_w1tc = SWIM_BIT;    // LOW
    GPIO.enable_w1ts = SWIM_BIT;
    esp_rom_delay_us(500);
}

for (int i = 0; i < 4; i++) {
    GPIO.enable_w1tc = SWIM_BIT; // HIGH
    esp_rom_delay_us(250);
    GPIO.out_w1tc = SWIM_BIT;    // LOW
    GPIO.enable_w1ts = SWIM_BIT;
    esp_rom_delay_us(250);
}

GPIO.enable_w1tc = SWIM_BIT;     // HIGH (رها کردن)
```

---

## 🔄 **۳. دریافت SYNC از دستگاه**
بعد از Entry، دستگاه (STM8) یک پالس SYNC می‌فرستد:

- **SYNC = 128 سیکل SWIM = ~16µs** (در 8MHz)
- اندازه‌گیری مدت زمان LOW برای کالیبره کردن تایمینگ

```c
uint32_t start = XTHAL_GET_CCOUNT();
while (!((GPIO.in >> SWIM_PIN) & 1)) {
    // منتظر Rising Edge
}
uint32_t sync_duration = XTHAL_GET_CCOUNT() - start;
uint32_t sync_us = sync_duration / 240;  // 240 cycles per µs
```

---

## 📝 **۴. فرمت بیت‌ها در SWIM**
SWIM از کد **Return-to-Zero (RTZ)** استفاده می‌کند:

### **Low-Speed Mode (8MHz):**
| بیت | LOW | HIGH |
|-----|-----|------|
| **1** | 2 سیکل (250ns) | 20 سیکل (2.5µs) |
| **0** | 20 سیکل (2.5µs) | 2 سیکل (250ns) |

### **کد ارسال بیت:**
```c
if (bit) {
    // بیت 1: LOW کوتاه + HIGH بلند
    GPIO.out_w1tc = SWIM_BIT;
    GPIO.enable_w1ts = SWIM_BIT;
    delay(SHORT_CYCLES);
    GPIO.enable_w1tc = SWIM_BIT;
    delay(LONG_CYCLES);
} else {
    // بیت 0: LOW بلند + HIGH کوتاه
    GPIO.out_w1tc = SWIM_BIT;
    GPIO.enable_w1ts = SWIM_BIT;
    delay(LONG_CYCLES);
    GPIO.enable_w1tc = SWIM_BIT;
    delay(SHORT_CYCLES);
}
```

---

## 📦 **۵. ساختار فریم (بایت)**
هر فریم شامل ۱۰ بیت است:

```
Header (1) + 8 بیت داده + Parity (1)
```

| بخش | تعداد بیت‌ها | مقدار |
|-----|------------|--------|
| **Header** | 1 | 0 (میزبان) یا 1 (دستگاه) |
| **Data** | 8 | داده اصلی |
| **Parity** | 1 | XOR همه بیت‌های داده |

### **کد ارسال بایت:**
```c
void send_byte(uint8_t data, uint8_t len) {
    uint8_t parity = 0;
    
    send_bit(0);  // Header
    
    for (int i = len-1; i >= 0; i--) {
        int bit = (data >> i) & 1;
        send_bit(bit);
        parity ^= bit;
    }
    
    send_bit(parity);  // Parity
}
```

---

## 🔧 **۶. دستورات اصلی SWIM**

| دستور | کد | توضیح |
|-------|-----|--------|
| **SRST** | 0x00 | ریست نرم‌افزاری |
| **ROTF** | 0x01 | خواندن حافظه |
| **WOTF** | 0x02 | نوشتن حافظه |

---

## 📖 **۷. توالی خواندن (ROTF)**

```
1. ارسال Command ROTF (0x01) + ACK از دستگاه
2. ارسال Len (تعداد بایت‌ها) + ACK
3. ارسال آدرس (3 بایت) + ACK
4. دریافت داده از دستگاه (N بایت)
```

### **مثال: خواندن Device ID از آدرس 0x4800**
```c
swim_send_byte(0x01, 3);  // ROTF
swim_send_byte(0x10, 8);  // Len = 16
swim_send_byte(0x48, 8);  // Addr High
swim_send_byte(0x00, 8);  // Addr Mid
swim_send_byte(0x00, 8);  // Addr Low

for (int i = 0; i < 16; i++) {
    swim_recv_byte(&id_data[i]);  // دریافت داده
}
```

---

## ✍️ **۸. توالی نوشتن (WOTF)**

```
1. Unlock فلش (کلیدهای 0x56 و 0xAE در 0x5062)
2. Erase صفحه (در صورت نیاز)
3. ارسال Command WOTF (0x02) + ACK
4. ارسال Len + ACK
5. ارسال آدرس (3 بایت) + ACK
6. ارسال داده (N بایت) + ACK
7. انتظار برای پایان نوشتن
8. Verify
```

### **Unlock فلش:**
```c
swim_wotf(1, 0x5062, &k1);  // 0x56
swim_wotf(1, 0x5062, &k2);  // 0xAE
```

## 📊 **۹. جدول آدرس‌های مهم STM8S003**

| آدرس | اندازه | توضیح |
|------|--------|--------|
| `0x4800` | 16 بایت | **Device ID** (فقط خواندنی) |
| `0x4000` | 2KB | **EEPROM** |
| `0x8000` | 8KB | **Flash** (قابل نوشتن) |
| `0x505B` | 1 بایت | **FLASH_CR2** (کنترل فلش) |
| `0x505C` | 1 بایت | **FLASH_NCR2** (مکمل) |
| `0x505F` | 1 بایت | **FLASH_IAPSR** (وضعیت) |
| `0x5062` | 1 بایت | **FLASH_PUKR** (کلید Unlock) |

---

## 💡 **۱۰. نکات کلیدی**
1. **مقاومت Pull-up ۱kΩ** الزامی است.
2. **همیشه Critical Section** برای تایمینگ دقیق.
3. **کالیبره کردن تایمینگ** با SYNC دریافتی.
4. **بعد از هر ROTF، دستگاه را ریست نکنید** (فقط SRST کافی است).
5. **برای نوشتن، حتماً فلش را Unlock کنید.**

### **۳. پیاده‌سازی STM32 Flash Write (نمونه)**

```c
// stm32_flash_write - نوشتن در Flash STM32
static proto_result_t stm32_flash_write(uint32_t addr, const uint8_t *data, uint32_t size) {
    // 1. Unlock Flash
    swd_write_mem(0x40022004, 0x45670123);  // FLASH_KEYR
    swd_write_mem(0x40022004, 0xCDEF89AB);
    
    // 2. Wait for Ready
    while (swd_read_mem(0x40022000) & 0x01) {}
    
    // 3. Erase Page
    swd_write_mem(0x40022010, addr);  // FLASH_CR
    swd_write_mem(0x40022010, 0x00000040);  // Start Erase
    while (swd_read_mem(0x40022000) & 0x01) {}
    
    // 4. Program (16-bit)
    for (uint32_t i = 0; i < size; i += 2) {
        uint16_t word = *(uint16_t*)&data[i];
        swd_write_mem(addr + i, word);
        while (swd_read_mem(0x40022000) & 0x01) {}
    }
    
    // 5. Lock Flash
    swd_write_mem(0x40022004, 0x00000000);
    
    return result;
}
```

# 📊 **توضیح پروژه L-Programmer - قابلیت‌های جدید**

## 🎯 **L-Programmer چیست؟**

**L-Programmer** یک برنامه‌نویس و دیباگر جهانی، بی‌سیم و مبتنی‌بروب است که با استفاده از **ESP32** و رابط کاربری وب، امکان برنامه‌ریزی و دیباگ طیف گسترده‌ای از میکروکنترلرها را فراهم می‌کند. این پروژه جایگزین طیف وسیعی از ابزارهای تخصصی (مانند ST-Link، J-Link، USBasp، CH341A و ...) خواهد شد.

---

## 🚀 **قابلیت‌های جدید اضافه‌شده:**

### ۱. **WebSocket Server مرکزی (پورت 8080)**

یک WebSocket Server قدرتمند و همیشه فعال که به تمام پروتکل‌ها و نرم‌افزارها امکان اتصال می‌دهد:

```
ws://192.168.1.17:8080/uart/terminal    → UART Terminal
ws://192.168.1.17:8080/swd/debug        → ARM Debugging
ws://192.168.1.17:8080/openocd          → OpenOCD Bridge
ws://192.168.1.17:8080/xvc              → Xilinx Vivado
ws://192.168.1.17:8080/spi/monitor      → SPI Monitor
ws://192.168.1.17:8080/can/obd2         → OBD-II Diagnostics
```

**✅ بیش از ۴۰ Endpoint اختصاصی برای پروتکل‌های مختلف**

---

### ۲. **پشتیبانی از پروتکل‌های متعدد**

| دسته | پروتکل‌ها |
|------|-----------|
| **سریال** | UART, RS485, Modbus, 1-Wire |
| **دیباگ** | SWD, JTAG, OpenOCD, CMSIS-DAP |
| **خودرو** | CAN, OBD-II, K-Line |
| **برنامه‌ریزی** | ISP (AVR), ICSP (PIC), Holtek ISP, CC-DBG |
| **صنعتی** | SPI, I2C, PWM, GPIO, ADC |
| **FPGA** | XVC (Xilinx), JTAG (Altera/Lattice) |
| **پیشرفته** | DMA, Register Access, Logic Analyzer |

### ۴. **ترمینال چندمنظوره (Full Duplex)**

- **ارسال/دریافت همزمان** داده از طریق WebSocket
- **پشتیبانی از ۲۰+ پروتکل** در یک صفحه
- **تنظیمات实时** (Baud Rate, Data Bits, Parity, Flow Control)
- **HEX Mode** و **Timestamps**
- **Script Editor** برای اجرای دستورات متوالی
- **Capture** و **Save Log**
